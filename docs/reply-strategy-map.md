# 观众事件回复策略全景（2026-09-29；保护与重排更新于 2026-10-10）

> 用途：回答「一条弹幕、SC、礼物、上舰、进房进来之后，她说不说、什么时候说、怎么说、被打断了怎么办」。
> 结论对着代码核过，带 `file:line`；依赖真端点而没量过的写「待验证」。
> **先看网页 [reply-strategy.html](reply-strategy.html)**：八步流程、可以自己点的模拟器、六个场景时间线都在那里。这份是它的文字版和出处清单。
> 姊妹文档：记忆和上下文见 [memory-map.md](memory-map.md)；
> 付费丢单那一类跨子系统问题，[review-2026-09-23.md](review-2026-09-23.md) 的 C2 已经逐条列过，这里只引用。

## 0. 先记住三句话

- **每条都记，不是每条都回。** 弹幕、礼物、进房全部写进记忆和面板。回不回是另一回事：弹幕太多时一次只挑一条，关注和点赞从来不回。
- **她只有一张嘴。** 同一时间只说一件事，其他的排队。主播在说话、她自己在说话、上一句还没播完，都不开口。
- **SC、上舰和付费礼物更耐等。** 包括小额付费礼物，它们排队时不设普通事件的 20 秒有效期，被主播打断后重新排队。免费或金额为 0 的礼物会过期、打断后不重排；普通弹幕默认也不重排，可单独开启一次补说，仍保留原有效期。发送失败后的重试另有期限，超时、断线等情况也可能终止答谢。

整条路分八步：收到 → 能回吗 → 走哪条路 → 排队 → 等时机 → 开口 → 被打断怎么办 → 说完记下来。
网页里每一步都写了「这一步在问什么、大多数时候怎样、没通过会怎样」。

表里没写但要知道的：

- **写进她历史的是什么**：一条带 `<bilisama_live_events>` 标签的条目，形如 `[SC] 阿强: 主播今天几点下播`。金额从不出现，模型没见过的数字就说不出口（`intents.py:125-150`）。
- **重排**：SC、上舰、付费礼物（含小额）被主播打断后回到同优先级队尾，不重复写已经记录的事件条目；duplex 再次派发时依据保留的原始事件重新代笔全文。每次打断只重新入队一次，重复回报不重复入队；付费事件再次被打断仍可重排，没有普通弹幕的补说次数上限。免费或金额为 0 的礼物不重排。超时、撞屏蔽词、断线仍不补说；紧急静音也不会补说。
- **抢占**：只在回复尚未输出时发生，而且必须严格更高；duplex 的保护期间也不允许抢占。其他后端保留原有规则，保护中的回复尚未输出时仍可被更高优先级事件抢占。已经输出后，其他观众事件都排队，哪怕是 SC（`scheduler.py` 的 `_maybe_preempt`）。
- **礼物累计**：分档看本次合并后的总电池数，不只看单价；小礼物连送可升到中档或高档。累计只覆盖同一条未结算连击，结算后的 10 分钟抑制期内，加送不会升级或追加此前的答谢（`events.py` 的 `Gift.total_battery`、`safety.py` 的 `GiftComboAggregator`）。
- **付费保护范围**：`protect_paid_replies` 只覆盖 SC 和高额礼物，与排队优先级分开判断。上舰、中额及小额付费礼物只重排，不进入保护窗；小额礼物优先级仍为 30。duplex 从实际开始播放计时，窗口内本地不因主播开口清掉这条答谢，但不能保证服务端继续生成音频；其他后端保留原有派发计时和服务端保护能力。

### 普通弹幕：保护和补说分别设置

系统 → 回复策略 → 普通弹幕有两个开关：「回复开头防打断」和「被打断后重新回复」，出厂
都关闭。保护开启后默认 2 秒；重排开启后默认概率 100%，可在高级选项中调低。高级全量配置
里的「互动」也能改同一组值。两项只管已选中的普通弹幕，不改变筛选、令牌或优先级。

- 保护不随机：duplex 从实际首播计时，0 毫秒不保护；付费答谢仍用自己的保护时长。
- 重排概率对每条弹幕只决定一次。第一次被打断后最多补说一次，第二次被打断就放下。
- 补说仍用原优先级和原截止时间：`max(到达时间 + 20 秒, 选中放行时间 + 5 秒)`。
  100% 不绕过有效期或发言权门，重排时不续期，也不重新抽取概率。
- 热更新影响随后创建的回复；正在排队、生成或播放的回复沿用创建时的规则。
- duplex 再次派发仍从原事件重新写稿，不从断字处续播。本地保护无法阻止服务端自行停声。

实现沿用 `director/intents.py` 的事件映射和 `director/scheduler.py` 的保护、重排路径；
配置由 `app.py` 的装配层传入，不在播放器里判断概率。具体人工步骤见 runbook 的
「普通弹幕的保护与重排」。

## 3. 三条共同规则

### 3.1 一张嘴

调度器同一时刻只有一个活跃回复，派发中、回复中、链路断开都不派下一条（`scheduler.py:656-660`）。队列是按 `(-优先级, 序号)` 的堆，没有长度上限。

### 3.2 发言权门

五个条件按顺序查，任一成立就等（`floor.py:139-163`）：

| 条件 | 含义 |
|---|---|
| 主播在说话 | 服务端报了 speech_started |
| 有一轮在进行 | 我们的回复，或她自己的麦克风轮次 |
| 音频还在播 | 本地扬声器或面板页面还有声音 |
| 静默窗口 | 主播刚停，等服务端判停的宽限 |
| 冷却 | 两次发言最短间隔；**生产里是 0，这一条不生效**（`dev_talk.py:2149`） |

静默窗口按后端不同：

| 后端 | 静默窗口 |
|---|---|
| DashScope、OpenAI GA | 0.6 秒 |
| 火山 | 1.8 秒 |
| duplex | 1.8 秒（协议没有判停参数，这个数是借的，待验证） |
| s2s | 1.9 秒 |

没有优先级能越过这道门。SC、上舰和付费礼物（含小额）在主播连续说话时会一直等，没有普通排队有效期；免费或金额为 0 的礼物仍会过期。

### 3.3 两个节奏器

- **令牌桶**：弹幕、普通进房、主动话题三家共用一个桶（`event_pacing.py:39`）。容量按话痨度 1/2/3，回充 8/12/20/60 秒按热度，再乘话痨系数 1.35/1.0/0.7。礼物、SC、上舰、贵宾不花令牌。
- **挑选窗口**：窗口长度和分数线随房间热度和话痨度变。

| 话痨度 | 冷清 | 稀疏 | 活跃 | 很热闹 |
|---|---|---|---|---|
| 低（桶容量 1） | 1 秒 / 分数线 0.30 / 回充 10.8 秒 | 3 / 0.35 / 16.2 | 5 / 0.39 / 27 | 11 / 0.43 / 81 |
| 中（桶容量 2，出厂） | 1 / 0.17 / 8 | 2 / 0.22 / 12 | 4 / 0.26 / 20 | 8 / 0.30 / 60 |
| 高（桶容量 3） | 1 / 0.10 / 5.6 | 1 / 0.10 / 8.4 | 3 / 0.14 / 14 | 6 / 0.18 / 42 |

热度按最近 60 秒的弹幕数、发言人数、进房人数、付费次数分四档，升档立刻、降档等 30 秒（`event_pacing.py:223-271`）。
分数线 = 话痨度基准（低 0.35、中 0.22、高 0.10）+ 热度加减（冷清 −0.05、稀疏 0、活跃 +0.04、热闹 +0.08），最低 0.1。2026-10-04 按 yiko 分支的数值下调，原来是基准 0.5 / 0.3 / 0.15、活跃 +0.05、热闹 +0.1。

## 4. 同一条回复在五个后端上

| 后端 | 怎么发 | 81 行事件合同送到了吗 | 主播插话多快被发现 | 付费保护 |
|---|---|---|---|---|
| OpenAI GA | 条目进历史，回复走旁路 | 送到，每轮替换会话指令 | 没量过 | 只有调度器那一半，服务端照切 |
| DashScope | 条目和回复都在带内 | 送到 | 约 330 ms | 只有调度器那一半；2026-08-25 实测服务端照切（#45） |
| 火山 | 条目和短指令拼成一条查询 | **没送到**，只有每类的短指令 | 没量过 | 只有调度器那一半；服务端会不会自己停，待验证 |
| duplex | 侧路模型先写稿，她照念（`speech_text_buffer.commit`） | 送到代笔的侧路模型，没送到念稿的她 | 约 850 ms；`reply_hold_ms` 旋钮可以扣住开头 | 从实际开始播放计时，只保护本地调度和播放；服务端是否继续输出不由这个开关保证 |
| s2s | 条目进历史，回复走旁路 | 送到 | 服务端先切再报，约 517/712 ms（p50/p90） | 完整：先关服务端的打断，再顶住 4 秒 |

duplex 另一条路线 `event_replies = "tool"`：弹幕只存着，她在自己的麦克风轮次里调工具拉取。这条路线下合同和短指令都到不了她，回答搭在她自己的轮次上，会被语音门判「先听」拦掉；主动话题和戳一戳在这条路线上关闭。出厂是代笔路线。

语音门只看她自己的麦克风轮次，事件回复全部绕过（`voice_turn.py:221-224`）。

## 5. 结局词汇：面板上每条事件的下场

调度器给每个意图记一条结局（`obs/outcome.py`）：

| 结局 | 含义 | 常见原因 |
|---|---|---|
| spoken | 说完了 | 听众听到的是 `@played`，没有播放回执的是 `@generating` |
| skipped | 没派发就放弃 | 链路断开、紧急静音、重复、duplex tool 路线已归档 |
| cancelled | 派发后被切 | 主播插话、被更高优先级抢、紧急静音 |
| failed | 出错 | 发送失败、撞屏蔽词 |
| expired | 排到时已过期 | 在发言权门前等太久、SC 被撤回 |
| timed_out | 25 秒没回完 | 客户端看门狗 |

**挑选车道和装配入口的丢弃不记结局**：暂停、说话开关关掉、令牌不够、挑选器筛掉，只有日志和计数，面板回答不了「她为什么没理这条」（见 §6 第 3 条）。

## 6. 现在有问题的地方（按对直播的影响排）

1. **火山上，她没拿到完整的「怎么回观众」说明。** 其他后端每回一条事件都附一份 81 行的说明，比如「弹幕里的『你』默认指主播」「不能说礼物是送给自己的」。火山没有逐条附加的通道，原计划是塞进会话设置，但代码从来没塞过，文档和注释却都写着塞了。所以火山上她只知道每类事件的一句话要求。出处：`app.py:403-418`；说法有误的地方在 `capabilities.py:41-46`、`volcano.py:888-892`、`docs/architecture-status.md:145-147`、计划 §15.22。
2. **暂停期间的 SC 和礼物，恢复后不会补谢。** SC 在暂停时直接没了。礼物更糟：合并好的感谢在暂停里被吞掉，还会挡住这个人之后 10 分钟内同一种礼物的感谢。出处：`app.py:213-214`、`app.py:281-282`、`selector.py:222-232`。
3. **面板上查不到「她为什么没回这条」。** 被筛掉、分不够、窗口里输了、额度用完、开关关着、暂停，这些都只写日志，面板上看不到。挑选器的跳过回调没接（`dev_talk.py:2194-2206`），`selector.py:17` 的注释却说接了。
4. **花了钱的也可能丢，也可能等太久。** 断线时排队的全丢；回复超时、说到屏蔽词被切的不会重说。反过来，SC、上舰和付费礼物（含小额）没有普通排队有效期，主播一直说它就一直等，可能几分钟后才谢。全分支 review 的 C2 列了六个洞。
5. **面板上「两次发言最短间隔」没有用。** 程序里写死成 0（`dev_talk.py:2149, 2356`），改面板上的值不起作用。
6. **没登录 B 站账号时，进房的人都被当成同一个人。** 匿名连接下只有弹幕能分清谁是谁。进房的人全算一个，一场只欢迎一次；不同人送的同一种礼物被合并成一个人的连击，只谢最后一个。看代码推出来的，没实测（`source.py:18-22, 196`、`selector.py:416-418`）。
7. **「挑着回」的分数线经常被绕过。** 弹幕里只要有「呢」「谁」「哪」，提到「主播」或「up」，或者和最近几句对话有两个字相同，就直接入选不看分。热闹的直播间里大部分弹幕都能满足其中一条（`scoring.py:59-67, 151-158`）。
8. **两份「怎么回」要手工同步，已经对不上了。** 每类一句话的要求写在代码里（`intents.py:153-226`），81 行的完整说明写在 `config/personas/live/event_responses.md`，改了一份容易忘另一份，现在已经有几条只在配置文件里有（台账 #94）。
9. **回复长度不统一。** 观众事件默认一句话（45 token）；主动找话题开播时是 120，要改一次面板才变回 45；戳一戳固定 40（`dev_talk.py:2245, 2310, 2760`）。
10. **duplex 上写稿的模型把「怎么回观众」的说明也套在主动找话题和戳一戳上**，而这两类本来不是观众事件（`dev_talk.py:2131-2140`）。
