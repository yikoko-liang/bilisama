当前状态：按最新约束实现了独立函数报告、事件状态、Prompt 和主动契机组件，
生产接线和礼物聚合成员精确撤销已完成；按需报告口径已更新，完整门禁通过，真实服务验收仍未通过必需状态报告项。
组件测试和完整服务验收分开记录，不能据此写成已经全面生效。

快照不含本机私人上下文，回复长度按变量展示。导出正确不等于真实语义验收通过。

实施边界：

- 语音与直播事件继续共享上下文，不拆成互相看不到历史的两套对话。
- 主播语音始终优先。是否适合开口、关联哪个事件等语义判断交给模型；
  程序根据明确的判断结果执行等待、取消、静默和重排，不增加语义关键词黑名单替代模型。
- 同一次 Realtime 生成维持原正文／`[SKIP]`；需要改变后台状态时才通过独立函数调用报告。
  普通问答、自语先听、讲解中沉默且没有新状态变化时，不需要报告空事件列表或 `keep`。
  具体事件处理进度、首次进入或解除持续静默、观点征集启动／取消／完成等变化，必须报告才能应用。
  不增加意图判断模型调用，不因工具回执再生成一遍回答，不把工具结果作为普通语音新的播放等待条件。
  意图、事件编号、JSON 和后台动作不能混入口播正文。
- 生产函数报告目前只在已实测支持的 DashScope `qwen-audio-3.0-realtime-flash` 上启用。
  其他后端不能仅凭共用界面或共享 Prompt 就算通过联动验收。
- 保留现有语音输出：接话直接输出正文，无标签、无判断过程；先听以 `[SKIP]` 起头，
  后接十字以内的观察，无法判断时只输出 `[SKIP]`。整条一行，不再接着回答。
  此约定只管主播语音，弹幕、礼物、进房继续使用各自事件规则；不能把后台 JSON、事件 ID 或工具报告塞入口播。
- `voice_addressing.md` 的“输出”块逐字保留，用测试与 `0d103a9` 的原文核对；
  输入和行为说明的调整不改写这个输出协议。
- 主播后来打字时，仍写入流水、记忆、蒸馏和共享上下文，但不因此打断正在生成或播放的回复，
  也不发起额外复核调用。后续自然生成读取新上下文后再更新相应事件状态。
  因而不能承诺晚到的文字答案一定阻止当前这句重复播报。
- 只调整本计划涉及的模块。保留现有直播 Mock、语音回放、事件流水、记忆、蒸馏与共享上下文。
- 不承诺模型一定判对。自动化检查、真实接口能力和真实多轮语义效果分别记录。
- 没有授权增加第二个判定模型，也没有新增该调用。按用户最新指令修正同次报告的调用条件，
  不再将是否增加独立后台模型列为本轮待确认选择。

## 2. 主播语音：先判断是否开口，再决定说什么

### V0. 输入信息与后台结果

输入包括主播当前语音、连续上下文，以及近期弹幕、礼物、上舰、进房、SC 事件。
事件应能区分编号、发生时间、观众昵称、UID、回复对象和处理状态，不能只有一段混合文本。
主播文字弹幕是主播的输入，不能误归为观众提问。

模型需要判断交流对象、此刻是否适合开口、关联的具体事件及其处理进度，
并在需要时交付静默状态或观点征集任务。下表是产品语义，不预先规定接口字段或强制新分类枚举。

| 编号 | 场景 | 目标行为与联动 |
|---|---|---|
| V1a | 自言自语：语义不完整、犹豫 | 不开口，持续监听后续内容。 |
| V1b | 自言自语：自我吐槽 | 可以自然接一句，也可沉默，不强行陪聊或连续追问。 |
| V1c | 自言自语：介绍接下来计划或动作 | 不开口，持续监听；不把主播的操作旁白当成给助手的任务。 |
| V2 | 面向观众长时间讲解 | 不开口，持续监听，直到判断讲解结束；短暂停顿不能自动算结束，结束也不强制补话。 |
| V3 | 面向观众收集建议、问题或观点 | 不立刻替观众回答，监控弹幕；将话题和征集起点交给主动话题管理器。 |
| V4 | 明确交代助手 | 可以直接叫名字，也可以无指代但语义明确；结合上下文识别，不要求每次叫对名字。 |
| V4a | 记录 TODO、发表观点、介绍背景、总结弹幕 | 使用真实上下文和直播事件完成可用任务；不能假装执行不存在的记录、操作或视觉能力。 |
| V5a | 主播语音回复弹幕 | 比对近期弹幕的语义、昵称和时间关系，确定对应哪条；结果交给事件管理器。仅念题或叫昵称不能算已答完。 |
| V5b | 确认主播正在回复弹幕后 | 可以沉默，也可以结合原问题和主播回答自然附和，不另起一轮重复回答。 |
| V6a | 主播谢礼、谢上舰、谢 SC 或欢迎进房 | 比对昵称、事件类型和行为，确认正在处理哪个具体事件；结果交给事件管理器。 |
| V6b | 确认主播正在处理答谢、欢迎后 | 可以知情附和，不能误认为刚发生了另一次礼物或进房。 |
| V7 | 软硬静默指令 | 对“安静、闭嘴、别说话、先停一下、我先补充、看看效果”等表达结合对象和语境理解；停止开口并持续静默，直到下一次适合开口的意图。 |

静默不靠固定词命中：主播说“这个视频先停一下”和要求助手停一下，需要模型区分对象。
新直播事件到达、原回复排队恢复、冷场定时到期都不能自行解除静默。
无名字的直接追问或新的明确委托，也可能是下一次适合开口的意图，不只接受固定“解除”口令。
后台静默状态只接受有效函数报告中的进入／解除动作；不凭正文、`[SKIP]` 或没有报告来推断状态变化。
静默已生效且主播继续讲解，没有新变化时无需反复上报进入静默。

## 3. 直播事件：与语音共享处理状态

| 编号 | 要求 | 目标行为 |
|---|---|---|
| E1 | 精确关联 | 用具体事件身份管理弹幕、礼物、进房、上舰、SC；同一用户的不同事件不能一起取消，同昵称不同 UID 不能混淆。 |
| E2 | 主播正在处理与已经处理分开 | 正在回答、答谢或欢迎时暂缓对应任务；确定完成后取消同一事件的独立回复。话题相近、念题、叫昵称都不能单独证明完成。 |
| E3 | 主播打字回复 | 文字进入流水、记忆、蒸馏和 Realtime 共享上下文，不触发独立回复或额外复核。模型在后续正常生成中依据身份、`@UID` 和具体答案关联问题；不能按用户整批取消。晚到文字不打断已经生成或播放的回复。 |
| E4 | 调度阶段与时间边界 | 已有有效模型结果时，在收集、待派发和排队环节去掉已处理项；主播语音打断按原话权流程执行，重排前重新检查事件状态。迟到结果不能误取消另一条新语音。不能把 E3 的后发文字改成即时停播。 |
| E5 | 保留未完成部分 | 一批弹幕只处理已答条目，其他继续保留；SC 仅感谢支持不等于正文问题已答完。 |
| E6 | 知情附和 | 主播处理过后，允许当前语音回合自然附和；独立事件任务取消，避免同一互动再播一轮。 |
| E7 | 弹幕口播要求 | 自然交代谁问了什么，再给实际回答。不能只复述问题，也不能机械套同一格式；已知信息自己答，需主播确认的事实或决定自然转交，禁止什么都转交。 |
| E8 | VIP 分档欢迎 | 按身份档次调整重视程度，先欢迎，再简短同步近期背景；不能只接上文而忘记欢迎，也不连续重复同一段简介。 |
| E9 | 欢迎类事件的播放时机与去重 | 主播正在讲话、解释或处理其他内容时，不把欢迎/进房/上舰误判成 `[SKIP]`，也不改变原事件身份；事件保留在原优先级队列，等当前语音回合结束后再生成并播放。只有共享处理记录明确确认主播已完成这一次欢迎或答谢，才取消独立任务；生成后确实被传输层打断时，才按已有的付费事件保护路径处理，不能把打断误当成已完成。 |

批量任务若已生成不可拆分的混合音频，不能承诺精准删掉其中一句。
需要停止整段时，应保留尚未答复的候选，不能把整批都标成已完成。
重排还要遵守静默与话权状态；“进入队列”不代表可以立即恢复播放。

## 4. 主动话题：保留原来源，新增可追踪的契机

保留直播事件、摘要和近期对话历史这些来源。新增候选不能绕过静默、主播优先或已处理状态。

| 编号 | 契机 | 目标行为 |
|---|---|---|
| P1 | 被打断的内容 | 主播语音回复、弹幕回复、送礼等不同来源中，真正被打断、没有重排、仍有价值且未解决的内容可进入冷场候选。 |
| P1a | 自然续接 | 先简短回顾原事件或问题背景，再继续；不能把旧事当作新发生，也不能和原重排路径重复恢复。 |
| P1b | 不得恢复的内容 | 已处理、无需回应、被明确拒绝、因静默指令停止、已进入其他重排的内容，不换成主动话题重新说。 |
| P2 | 主播征集观点 | 语音识别出面向观众征集后，记录话题和语音起点，收集之后窗口内的相关弹幕。配置为 `interaction.proactive.collection_window_s`，默认 120 秒，可设 5～1800 秒。 |
| P2a | 交付总结 | 归纳共同意见和不同角度，告诉主播；到期等待话权和静默状态允许，不必等全房冷场。主播提前要求总结时提前交付。 |
| P2b | 时间和内容边界 | 不把征集前的旧观点、无关弹幕或并不存在的观点混入；没有有效反馈时不捏造共识。话题取消或被替换时不得继续交付旧任务。 |
| P3 | 观众自发讨论 | 由模型识别有效弹幕话题，排除主播已回复、纯互相回复和低信息内容；观察大家在讨论什么，向其他观众发起深入讨论或从一个观点展开。 |

普通冷场循环继续检查主播话权、空闲时长、预算和普通待处理事件。
征集到期是另一种触发条件：不等全房冷场，但仍等待主播话权和静默状态允许，
对应 `src/bilisama/proactive.py` 的 `_submit_opinion_summary`。
征集窗口结束后最多再等待 300 秒；中断候选最多保留 8 条、每条 300 秒。
这些是内存与时效边界，不是模型已判定内容无价值，也不能把有限记录说成全体观众意见。

#### P0 的实际探测结果

以下探测使用独立连接，不代表完整产品链路验收。结果保存在本机
`outputs/voice-event-linkage/`。早期探测时尚未修改生产代码，后续实现状态以上面的当前状态为准。

| 探测 | 实际结果 | 能说明什么、不能说明什么 |
|---|---|---|
| 要求先返回控制结果，见 `probe-control-first.jsonl` | 1 次静默场景只返回控制结果且无音频；2 次允许开口的场景也只有工具结果，没有音频。 | 控制结果可以独立返回；不能依赖“先工具再回答”的文字要求保证同次生成继续口播。 |
| 要求正常回答并返回控制结果，见 `probe-control-after.jsonl` | 2 次文本输入都在同次生成得到口播和工具结果，转录未混入工具 JSON；仅确认工具结果后观察到 0 次自动新回复。 | 这种输出组合可行，但两次文本输入不足以证明真实语音下顺序稳定。 |
| 既有 Seed 音频实时输入，见 `probe-audio-results.jsonl` | 使用 16 kHz PCM，服务端语音停顿阈值 600 ms。前 3 轮完成：直接提问产生语音和控制；向观众征集无音频且给出话题；停止指令无音频且进入静默。 | 真实语音也能同次生成控制信息；只证明这些观察，不代表完整多轮验收通过。 |

真实语音探测同时暴露了三个限制：

- 第 1 轮问“什么是工具调用”，口播转录提到了内部 `report_interaction`，
  尽管 Prompt 禁止透露。这是控制机制泄露，不能称为干净口播或通过正式验收。
- 第 1 轮首音频在输入起点后 4686 ms 到达，完整控制结果在 5373 ms 到达，晚了 687 ms。
  但实验 Prompt 明确要求先输出语音消息、再调用工具，见
  [probe_audio_control.py](../outputs/voice-event-linkage/probe_audio_control.py) 的 `main` 中 `instructions`。
  这只说明新增工具报告的到达顺序，不能推断模型先说话后判断，也不能据此要求现有语音增加等待。
  生产版仍在同一次 Realtime 生成中选择正文或 `[SKIP]`，见
  [voice_addressing.md](../config/personas/live/voice_addressing.md) 的“输出”节，
  由 [voice_turn.py](../src/bilisama/director/voice_turn.py) 的 `_judge` 根据回复开头决定是否放行。
  687 ms 也不是固定延迟或所有场景上限。
- 第 3 轮的静默动作符合预期，但交流对象返回 `self`；完整对象分类仍有问题。
  第 4 句又被语音停顿检测切成多轮，探测收集器在首个取消回复处结束，未能归属后续回复。
  因此这部分不能作为解除静默或连续状态保持的通过证据；后续出现的回复也不能直接归因于工具确认，
  它可能来自尚未说完的原句。

#### 已确认的实现取舍

现有主播文字弹幕由 [app.py](../src/bilisama/app.py) 的 `on_event` 和 `_write_anchor_context`
写入共享上下文，经 [hosted.py](../src/bilisama/realtime/providers/hosted.py) 的 `add_context_item`
到达 [client.py](../src/bilisama/realtime/client.py) 的 `send_command`，等待当前生成结束才发送。
如果旧回复已生成完、只剩本地音频播放，原次推理已经结束；同文件的 `_on_done` 和 `_settle`
记录生成终态并释放生成位置，不等于本地播放也已经结束。
所以仅把主播稍后打出的答案补入历史，不能保证旧回复立即重新判断并准确停播。

用户已确认不做后发文字的额外复核，也不因后来打字去中断当前生成或播放。
文字保留在共享上下文中，由后续正常生成读取；届时有明确事件报告才更新对应状态。
这保留了原语音体验和调用次数，但不保证已经开始播报的旧回答能避开刚到的主播文字答案。

撤回此前把新工具报告当成所有语音播放前置条件的提议。保留原有正文／`[SKIP]` 播放判断；
新增后台状态如何与其他事件联动仍需逐步验证，不能默认其时序已经可靠，也不能增加调用与等待。

#### 保留原输出协议后的探测

- `probe-preserved-output2.jsonl`：第一轮把发布问题标为 `handled`，但第二轮静默只输出 `[SKIP]`，没有函数报告。

#### 报告调用口径更正（2026-09-14）

用户明确：函数调用用于改变后台状态，不是每句话都必须交一份报告。
取消“每轮空事件列表加 `keep`”要求，也取消“没有函数调用一律异常”的判定。

| 当前回合 | 是否要求函数报告 | 验收重点 |
|---|---|---|
| 普通问答、自语先听、持续讲解，没有后台状态变化 | 不要求 | 正文或 `[SKIP]` 符合对象与时机即可；没有函数调用不报缺失错误。 |
| 主播确已回答、感谢或欢迎某个具体事件，或明确改变处理进度 | 要求 | 具体编号、状态与主播证据一致，不能靠正文猜已完成。 |
| 首次要求持续静默，或出现适合开口的新意图需要解除静默 | 要求 | 明确报告 `enter` 或 `release`；只说了正文或 `[SKIP]` 不改变后台静默状态。 |
| 观点征集启动、取消或已交付总结 | 要求 | 报告对应的 `start`、`cancel`、`finish`，不反复启动同一征集。 |

新词稿和运行期处理按以上边界更新，校准测试须先标明是否需要后台变化，再检查有没有正确报告。
无需报告与必需报告两组分开计数；不覆盖旧探测，不增加第二个判定模型。
运行期只把没有调用记入中性的 `without_report` 数量，不发缺失告警，也不能自行认定这轮是否漏报。
必需变化的缺失由带明确场景预期的验收核对，不能把这项计数当作失败数。
按需报告的程序回归已先观察到五项失败再修复：报告消费者 12 项、端到端连接检查 5 项、
生产装配结构检查 3 项，共 20 项通过。覆盖普通正文、讲解 `[SKIP]`、已静默时继续讲解无需报告，
没有缺失警告或二次生成；后台解除静默须有有效 `release`，普通口播仍不等待新增报告。
这组是假模型结果下的程序行为验证；完整门禁已通过，真实条件复测见验收文档，必需状态报告仍未可靠返回。

不以 Prompt 字符串出现了某句话或模拟模型返回正确结果，宣称这些语义能力已通过。
