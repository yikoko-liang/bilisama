## 1. 全景：仓库今天长什么样

### 1.1 一句话

整个产品是一条从「B 站房间」到「她开口」的单向水管，分四段，方向只有一个：

```
L4 ingest/            B 站原始消息 → LiveEvent，一窗一胜者
      ↓
L3 director/ persona/ memory/ + app.py Assembly
                      事件 → Intent（带优先级和判决），拼提示词，
                      保证任何时刻只有一条回复在飞
      ↓  只经 realtime/link.py 的 SpeechLink 协议 + 12 种归一化 LinkEvent
L2 realtime/          把「让她说这个」翻成五家后端各自的协议帧，再翻回来
      ↓
L1 ui/ + web/js       画帧、发开关、在页面里开麦克风和扬声器
```

`dev_talk.run_director`（dev_talk.py:1687 起，一个 2063 行的函数）把四段装起来。

SpeechLink 这条边界是全仓唯一有测试守着的边界（tests/unit/test_dependency_direction.py:39-47：director / persona / memory / ui / tools 五个包不许 import `realtime.providers`、不许出现三个 OpenAI 协议字面量），也是真正成立的抽象：L3 确实不知道协议。

产品的重心不在任何一层，在两个接缝上：

- SpeechLink 下面有三份手抄的传输状态机（client.py、volcano.py、duplex.py），本周主打的 duplex 是第三份。
- dev_talk.py 里那张热改钩子表决定「面板改的每个字段会不会当场生效」，它住在一个测不到的闭包里。

### 1.2 逐子系统

下面每段回答三件事：它是什么、关键文件、新人必须知道的决定。这部分是为了重新认路，不是挑错。

#### realtime 核心（link / client / dialect / capabilities / providers 注册表 / factory）

L2 的骨架。link.py 定义唯一对上暴露的接口 SpeechLink 和一组归一化事件 LinkEvent；ReplySpec 说「想让她说什么」，不说协议怎么发。client.py 是三个说 OpenAI-Realtime 方言的后端（s2s、DashScope、OpenAI GA）共用的 WebSocket 传输层：单响应槽位（同一时刻只许一个回复在生成）、25 秒看门狗、墓碑表（结算过的 response id 再来帧一律丢，但见 §5 realtime 第 2 条）、断线重连阶梯。dialect.py 把 GA / beta 两套线上事件名翻成内部名。capabilities.py 是每家后端的能力表。providers/__init__.py 是注册表加地址解析（命令行 > 配置 > 环境变量 > 内置默认）。factory.py 挑适配器类。

必须知道：协议差异只许住在 Codec 和 Capabilities 里，client.py 不出现 `if provider`；能力位原则上不上穿 L3，例外有两个（不是头注说的一个）：`composes_on_demand` 和 `per_reply_base_instructions`；断线和会话到期换连接走同一条结算路径：在飞回复全 FAILED → LinkDown → LinkUp。

纠偏：只有 hosted.py 和 s2s.py 从注册表拿 codec 和 caps；volcano.py 只 import volcano_wire，duplex.py 一个注册表符号都不 import，两者都从 client.py 借 SessionRefused。

#### OpenAI 方言的两个适配器（s2s.py / hosted.py）

s2s.py 对接我们自己打过补丁的 speech-to-speech 服务；hosted.py 一份代码同时服务 DashScope 和 OpenAI GA，差异靠数据表（能力位、编解码、PROFILES）。三条决定：协议规定每条回复自带的 instructions 会替换会话级人设，所以两个适配器都用 compose_instructions 把人设和本轮要求重新拼一遍（providers/__init__.py:247-275）；s2s 的回复永远走旁路（`conversation="none"`，不进服务端历史），hosted 按能力位决定：GA 走旁路、DashScope 走带内，带内回复服务端自己记历史，所以 hosted 的 add_context_item 遇到 assistant 角色直接丢掉（hosted.py:291-307）；hosted 的音色和判停参数只在连接引导帧里发一次，改动靠换 socket。

纠偏：openai_ga 是开发期参照不是出货路径（factory.py:198-201、台账 #82「真端点未验」），没有契约测试；付费保护（关掉主播打断）只有 s2s 真做，而且 `protect_paid_replies` 出厂是关的（台账 #91）。

#### 火山的两个适配器（volcano.py / volcano_wire.py / duplex.py）

volcano.py 是旧的端到端对话协议：二进制帧、编号事件、「连接→会话」两级握手；volcano_wire.py 是它的纯函数编解码器。duplex.py 是新的全双工协议：JSON 文本帧、OpenAI 风格事件名，但它不会自己组稿（`composes_on_demand=False`），弹幕回复由 L3 代写台词，它照着念。两个适配器都没复用 RealtimeClient，各自重写了槽位、看门狗、重连梯子、暂停/恢复。

必须知道：回复归属靠协议自己的线索，volcano 用 question_id 加墓碑名单防「取消后的尾帧变成占槽位的幽灵回复」，duplex 靠 `tts_type` 区分我们点的和她自己起的（后者过语音门）；duplex 的历史只在 session.create 时生效且必须偶数成对，所以 add_context_item 只暂存到下一次建会话；本周 duplex 加了三件事：reply hold（回复开头扣住 N 毫秒，出厂是 0 也就是关的）、speech-edge 兜底（转写结束帧丢失时静默 1 秒自己收尾）、发现 `speech_text_buffer.commit` 才是能起一轮的通道。

纠偏：台账 #105（重连时她自己说过的话进两遍历史，09-21 实测未修）是这块唯一挂着的已知 bug；台账 #104 末尾仍写「出厂默认仍是 tool」，代码已是 ghostwriter。计划第 3856 行明文「等第三个非 OpenAI 方言的 provider 出现时再谈抽取」，duplex 就是第三个，这笔账到期了。

#### director（scheduler / floor / intents / voice_turn / turn_protocol / output_guard）

产品的嘴巴调度中心。所有想让她开口的来源（SC、礼物、上舰、进房、弹幕、主动话题，加上主播说话触发的隐式回合）先变成 Intent，排进 scheduler.py 的堆，由它保证任何时刻只有一条回复在飞。三条决定：每条 Intent 以且只以一个 Verdict（「刚才为什么没说」的机器可读记录）收尾，这是几乎每个分支都写 `_emit` 的原因；抢占只在对方还没出声时发生，已出声的句子只有主播插话、恐慌按钮、输出守门命中敏感词能砍；主播自己的语音回合不是 Intent，调度器只登记它，唯一杀它的入口是 skip_implicit，语音门（voice_turn.py）在扇出泵里同步判断回合开头有没有 `[SKIP]` 记号。

纠偏：duplex 上 ReplyStarted 和整段文本一起发（duplex.py:1058-1066），`output_started` 在开口瞬间就置真，所以那家上派发后的抢占从不发生；语音门 0.6 秒和 reply hold「取 max 不相加」的原因是 hold 期间文本已流进适配器缓冲，放出时记号已在爆发里，如果哪家是音频先到的形态，就变成相加（voice_turn.py:275）。

#### 装配与入口（dev_talk.py / app.py / cli.py / proactive.py / event_pacing.py / side.py）

`bilisama dev-talk --director` 经 cli.py 到 dev_talk.run_director，把人设、记忆库、蒸馏器、主动话题、调度器、弹幕源、语音链路、本地声卡、面板服务器和桌宠壳一次装起来。app.py 的 Assembly 是事件到说话的漏斗：每个事件先落记忆，再过暂停门、说话开关、进房归并、弹幕筛选，最后变成 Intent。proactive.py 在冷场时用侧路模型（便宜的聊天补全接口，side.py）后台备话题。event_pacing.py 按最近 60 秒热度分四档。

必须知道：说话开关在 L3 之上判，Assembly 判了三次（on_event、_submit_event、deliver_entries），proactive 另在 dev_talk 的 proactive_submit 判，戳一戳完全不看开关（台账 #48 等拍板）；面板编辑走固定链：校验、改内存、跑热改钩子、落盘、失败回滚；run_director 里几乎所有东西是闭包，测试只能整场跑一遍或把源码当字符串断言。

#### ingest（events / sources / bilibili/source / selector / scoring / safety）

进水口。外层 events.py（铁律：uid 被打码成 0 也不能丢事件）和 sources.py（Source 协议、QueueSource、带退避重启的 SupervisedSource）。内层 bilibili/：source.py 用 vendored 的 blivedm 收包，付费事件走不丢的侧口袋，普通事件走有界队列；safety.py 三件带状态的小工具：去重环（0.35 秒回看）、熔断器（60 秒内 3 次失败锁死）、礼物连击聚合器（空闲 1 秒结算，结算后同 combo 压 600 秒）；scoring.py 先做三态判定再打 0..1 分；selector.py 串起来：去重→文本信号→跨人重复→打分→一窗一胜者，主播说话时把胜者暂存。

必须知道：ingest 自己不消毒，intent 路径的消毒在 director/intents.py 的 neutralize_tags；但 memory 一侧另有三条读路径今天没有边界（见 §4 C6）。source.py 也直接用 safety 的两件（自己的熔断器每次重启 reset；30 秒去重环合并上舰双发），selector 那把熔断器永不 reset，两把行为不同。仓库里没有任何输入侧屏蔽词过滤，唯一词表在 director/output_guard.py，只管模型输出。

#### ui 后端（server / hub / audio / config_edit / live_mock / poke / room_control / test_runner ...）

dev-talk 进程里内嵌的 FastAPI。鉴权一道：启动随机 token 作路径前缀，只绑 127.0.0.1，WebSocket 升级核对 Origin。两条 WebSocket：/ws 控制口走 UiHub 广播，每客户端 256 帧有界队列、满了丢最旧；/audio 音频口点对点二进制，由 AudioBroker 决定谁持有麦克风和扬声器（shell 压过 browser）。三条决定：音频不走控制口，因为「广播+丢最旧」对采样是错的策略；页面对音频连续性不可信，服务端 100 毫秒没声自己补静音保住服务端 VAD 的时钟；信任模型是单用户本机，`?role=shell` 只是查询串。

纠偏：产品真正走的 apply_runtime_config_edit 放行 LIVE + RECONNECT + RESTART 三类（config_edit.py:164-169），不只 LIVE；四个 session-only 路径根本不写 TOML（dev_talk.py:130-137）；回滚只覆盖 OSError 一族。

#### ui 前端（panel.js / main.js / audio.js / ws.js / capture-worklet.js / bubble.js / renderer.js / live-mock.js）

无框架原生 JS 约 3200 行，只做三件事：把广播的帧画到屏幕、把用户点的开关原样发回、在页面里开麦克风和扬声器。三条决定：后端是唯一真相，按钮只「问」，画面由 panel.state 回显来改；音频住在页面里，因为 Chromium 的回声消除只能减掉它自己放的声音；能原地更新就不重建 DOM，为了保住焦点和打开的下拉。所有动态文本走 textContent，唯一一处写入内容的 innerHTML 在 skins/fallback.js:26。重连时 main.js:424-428 在 everConnected 之后先 panel.reset() 再吃回放，时间线不会翻倍。

纠偏：面板本地上限（FEED_CAP=200、LOG_CAP=500）和服务端环（300/400）不相等。

#### 底座（config / persona / memory / obs）

config：schema.py 只放类型和默认值，validate.py 放跨字段规则，loader.py 四层叠加（随包默认、基础文件、随包 profile、用户 profile、面板改动）再跑 migrate.py，persist.py 把面板改的单个值写回用户层 TOML（active_profile 例外，写回基础文件），ui_meta.py 是设置页的字段说明书。persona：loader.py 读两份人工锚点（identity / personality），管两份机器长出来的文件（relationship / voice），蒸馏器没有通往锚点的代码路径。memory：store.py 是 SQLite，distill.py 用侧路模型做滚动摘要和场末批处理，context.py 把记忆行变提示词段落。obs：logging.py 的 JSON 事件日志（事件名常量，凭据和弹幕正文脱敏），outcome.py 每条发言的终局判决，health.py 探针。

## 2. 健康结论

分层是真的：L3 确实不知道协议，SpeechLink 这条边界经得起两个方向的追问，从进水口到嘴巴的数据流一条线能讲清。

病在两个接缝，而且都是本周刚到期的账：三份传输状态机各修各的疤（§4 C1），duplex 作为第三份抄本把前两份的坑各漏了一半；热改通道和 duplex 的文档在一周四次改结论后没跟上（C3、C5）。最贵的一条是出厂配置下面板在出货后端上整个只读（C4），门禁没抓到是因为 gate.sh 只用 s2s 跑 validate。

这不是要重写的仓库，是要还两笔到期账再往前走的仓库。先还 C1 和 C4，其余按 §3 的顺序。

## 6. 值得说出口的好东西

下一个人可能会想「清理」它们，别。

- **每条 Intent 恰好一个 Verdict。** scheduler 里几乎每个分支都写 `_emit`，看着啰嗦，但「她刚才为什么没说」有机器可读的答案，obs/outcome.py 的统计靠它。合并了这些分支，排障就瞎了。
- **假服务端故意比真端点难伺候，违规记账不 raise。** mock_realtime 的投机窗口按已追加音频量而不是墙钟关闭，mock_volcano 的握手必须两级。这些是真端点量出来的脾气。C10 说的是三份没对齐，不是这个思路错。
- **注释带日期和 commit 号讲「为什么改」。** link.py:8-13、dev_talk.py:1652-1668、client.py:433-436。这种注释是本轮评审能定位漂移的原因。
- **两道 AST 门禁：依赖方向和日志词表。** 让「L3 不认协议」「事件名是常量」从散文变成会红的测试。C7 和 C8 讲的是它们该再长两条，不是它们多余。
