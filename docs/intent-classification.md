# 直播互动场景与助手行动验收

版本：2026-09-08，v2。配套：[测试表与多轮脚本](intent-scenarios.md)。

2026-09-09：当前测试页另提供七类意图的简单集与用户 Excel 的 18 组困难集，
见 [运行说明](intent-test-console.md)。本文的场景划分保留作设计参考；分类模块仍未接入。

本版按主播正在做什么来组织测试。核心验三件事：助手回给谁、该不该回、什么时候回。回复措辞、知识详略和人设表现不作为这一轮的主要评分项。台词和事件均为模拟设计，不是候选主播的直播实录。

## 1. 场景分类

| 编号 | 主播互动场景 | 需要分清的变化 | 助手的目标行为 |
|---|---|---|---|
| S1 | 说话：自言自语 | 自问自答、操作旁白、给其他工具下令，转为向助手求助 | 先听，不逐句接话；真的被求助后回应主播 |
| S2 | 说话：讲解中 | 连续讲课、反问观众、停顿组织语言，转为交接或出现重要反馈 | 不抢讲解；交接时补充，重要漏信息等句末提醒 |
| S3 | 说话：观点讨论 | 主播与助手讨论、面向全房讨论、点名观众、观众互聊 | 认准对象；自然参与但不替观众作答，主播继续说时让话 |
| S4 | 说话：回答弹幕或互动 | 读题、正在答、只答一半、答完、出现新追问 | 读题不等于委托；只补未处理部分，已解决的待答任务取消 |
| S5 | 说话：感谢送礼 | 正在谢、已谢、漏谢另一位、委托助手谢 | 只接未处理的答谢，不抢话、不串送礼者 |
| S6 | 说话：欢迎进房 | 亲自欢迎、已欢迎、漏掉另一位、转回正题 | 不重复欢迎；空档补漏，不拖住已经恢复的讲解 |
| S7 | 静默：等待模型输出 | 自由等待、专注盯进度、明确暂缓、生成完成、主播回场 | 自由空档可接问题或暖场；专注时不说；任务恢复就结束暖场 |
| S8 | 静默：观看模型效果 | 看样片、听配音、看演示、暂停评价、重新播放 | 播放时不盖住内容；媒体问句不当指令；暂停讨论时再加入 |

同一段直播会跨多种状态，不能分类一次后整段不更新。判断只用已实际输入的线索，不能偷偷使用测试员知道的画面或心理活动。

## 2. 每种场景都测三种参与方式

| 编号 | 助手参与方式 | 行动条件 | 需要避免 |
|---|---|---|---|
| R1 | 被动响应指令 | 主播或观众确实在问助手，或主播明确交办 | 读题、台词、反问、对其他工具下令都当成请求；被问到仍不回应 |
| R2 | 作为直播间参与者 | 话题开放且出现自然空档，可短接观点、情绪，也可不说 | 每个停顿硬接一句；打断讲解；替全房表态 |
| R3 | 作为伴播 | 重要问题被漏掉、需要主播确认、等待空档适合暖场 | 基础问题全推给主播；重复答谢；专注或播放时强行暖场 |

三种方式是测试角色，不是用户每次手动选择的模式。目标是随互动切换。R2 的合理沉默可以通过；R1 的明确求助、R3 的重要补漏不能靠一直沉默通过。主动参与不要求每次先被点名。

## 3. 输入对象和输出对象分别记录

主播说“豆腐，帮我跟大家说明一下进度”：输入对象是助手，输出对象是全房。观众向主播问基础问题，助手代答时输出应对准该观众。必须由主播决定的问题，才在空档交给主播。

| 每步判定项 | 记录内容 |
|---|---|
| 当前互动 | S1—S8，以及刚发生的状态切换 |
| 输入来源与对象 | 主播、具体观众、媒体或其他工具；没有证据时保留不确定 |
| 应答要求 | 必须回应、禁止回应、条件成立才回应、可选参与 |
| 输出对象 | 主播、具体观众、全房；静默时为“无” |
| 行动路径 | 监听、等待、回答、短接讨论、暖场、补漏、交主播、停止、取消 |
| 有效期 | 允许开口的条件，以及等待、终止或取消的条件 |
| 原事项 | 哪位观众的哪条问题/行为；未处理、部分处理、已处理 |

典型路径：收到观众问题 → 主播还在讲，等待 → 主播只答一半 → 空档补剩余部分 → 主播重新开口，助手让话。如果主播已完整回答，应转成“取消旧任务”。

共享上下文保持不变。静默或取消回复不等于删掉语音、弹幕或记忆，来源和事项归属仍要保留。

## 4. 时机怎么测

本次不另设产品冷却阈值，先检查可观察的交接条件。

- 开口前：主播表达完整且没有继续同一段话；未要求安静观看/收听；原事项仍有效。
- 等待时：主播已经回答、取消了问题、恢复讲解或切换任务，原决策应更新；排队不等于必须播出。
- 输出时：主播拿回话权就停止；普通新事件不应把正在说的一句切碎。主测试固定关闭付费保护。
- 叫停后：不续播已取消内容；仍有效的交办也需重新获得话权。
- 生成完成/播放结束：须有模型真正收到的口述或状态线索，不能以测试员看见的屏幕变化作判据。

短暂停顿步骤默认留 5 秒观察窗；讲解或播放按脚本继续到结束。5 秒仅是统一测试操作，不是产品参数。主动话题步骤先记录本次配置的资格时间，再观察到该时点；没有资格日志时记录配置及实际等待时长，不把未满足计时条件算成意图失败。

脚本要求“助手正在说时”插入的步骤，必须在真实播报期间触发，不能等满观察窗。若助手已经结束，这次无法验证打断，记“无法判定”并重跑；不伪造尚未结束的状态。

回应时延从“输入完成且已允许开口”到实际首声。禁言窗口内抢话记失败；没有开口时检查过滤、预算、服务和播放是否正常。尚未建立基线，不虚构统一的合格毫秒数。

## 6. 执行和记录

48 条主场景 = 8 种主播状态 × 3 种助手参与方式 × 2 类主播，每条至少四轮。每案另有一个关键条件对照描述，不作为额外已执行案例计数。

1. 在“测试主表”筛选场景和模式，再按编号到“逐轮操作”执行。
2. 使用独立测试会话，不清真实记忆。固定模型、人设、话痨、语音/事件开关；主测试话痨为 medium。把配置与录音/日志位置记在结果区。
3. 前置布置、理想行动、后续输入仅供测试员。单列的“可见前文”需要在开测前实际输入，等当前回合结束再开始编号步骤；不预填理想助手回复。逐步输入真实语音和平台事件，不把完整剧本发给模型。
4. 下一步承接实际助手输出。若前步漏答或答错，先记录，不塞理想回复再算通过。
5. 分开填对象、应答选择、时机三项结果：通过、失败、未测、无法判定。措辞好听不能抵消抢话；断连或静音导致没声音不能算懂得沉默。
6. 原案和对照都跑，再按 low/medium/high 复跑重点场景。话痨只改变可选参与频率，不能改变身份、已处理状态和话权。正式音频验收每组重复三次。

先分八种场景、三种模式、两类主播看缺口，再分别统计对象错、误开口、明确求助漏接、重要信息漏补、抢话、重复接。可选参与不混进“必须回复”的漏接率。没有分类器输出时，只报告交互行为，不能宣称测出意图准确率。

共用边界变体：句中停顿、轻附和与真正叫停、同一句话换对象、主播自发弹幕、观众互聊、媒体喊助手名、短时弹幕/进房涌入、暂停和恢复。主播弹幕仍记录，但不作为新观众问题触发回复。

## 7. 素材与状态

方法参考将“是否对助手说”和“是否轮到助手说”分开测：[Apple 语音指向识别](https://machinelearning.apple.com/research/voice-trigger)、[Full-Duplex-Bench](https://github.com/DanielLin94144/Full-Duplex-Bench)、[TurnBench](https://github.com/SesameAILabs/turnbench)。研究结果不是本产品的达标证据。
