记忆库 memory.db 里到底存了什么

四张表、每个字段干什么、一条弹幕进来之后哪些行会变、谁在什么时候来查。

2026-10-03，对着 src/bilisama/memory/schema.sql 和 store.py 逐字段核过，例子取自本机 ~/.local/share/bilisama/rooms/dev-talk/memory.db 的真实行。全景见 docs/memory-map.md。

先记住三句话

一个文件，四张表两张流水账（stream 每场一行、event 每件事一行），一张累计表（viewer 每个观众一行，越来越厚），一张结论表（fact，蒸馏写的短句）。SQLite，标准库，没有 ORM，没有向量。
不用模型的部分每条都记，当场写每个事件两条 SQL：event 插一行，viewer 那个人的行加一笔。同步写在事件循环上，微秒级。暂停、静音、主播自己打字，照记。「阿强第五次来了」就是一句 SELECT streams_seen。
事件 7 天删，观众永不删，结论整组覆盖event 行启动时删掉 7 天前的。viewer 行永远留着，它就是全部意义所在。fact 按「哪方面、谁的」先删后插，所以表永远不会无限长。

四张表，每个字段

颜色区分表。右侧例子是真实行。标 写不读 的字段今天有人写、没人读；标 索引 的是查询靠它快。

stream 一场直播

开播 begin_stream() 插一行，下播 end_stream() 填 ended_at。进程里只记住当前这一行的 id，之后每个事件都挂在它下面。

字段作用例子
id主键这一场的编号。event.stream_id、viewer.last_stream_id、fact.subject（本场摘要）都用它161
started_at开播时刻，UTC ISO 字符串。「开播 1 小时 47 分」和「本周第 N 场」都从它算2026-09-22T03:45:22.315734+00:00
ended_at写不读下播时刻。只有 end_stream() 写它，全仓没有读者。为 NULL 说明那场没正常收尾NULL（本机 169 场里 69 场）
寿命：永久，从不删。本机 169 行。

event 一件事

每个进来的直播事件一行，不管回不回、说话开关开没开。按时间倒序取最近 N 条给蒸馏和主动话题。

字段作用例子
id主键自增，「最近 30 条」就是 ORDER BY id DESC11346
stream_id索引哪一场。读的时候永远只看当前场161
kind事件种类，十种之一：danmaku、gift、super_chat、guard_buy、vip_enter、entry、follow、like、share、room_statedanmaku
identity谁。uid:15247、被平台打码时 hash:41cf8adf、两者都没有时 anon。和 viewer.identity 同一把钥匙，但没有外键hash:41cf8adf
uname当时的昵称。主播自己发的弹幕写成「主播本人·名字」，防蒸馏把它读成观众请求老***
text弹幕或 SC 正文；礼物、进房为空NS2百亿补贴最低的，我刷到过2732的
value_cny花了多少钱，统一折成人民币；非付费事件为 00.0（一条礼物行：0.1）
wall_at索引发生时刻，UTC。7 天清理就是 DELETE WHERE wall_at < 七天前2026-09-22T04:21:19.342957+00:00
寿命：7 天（retain_event_days），只在启动时清一次。本机 650 行，进房占 575。

viewer 一个观众的累计

每个事件顺手 UPSERT 一笔。「常客感」整个靠这张表：来过几场、说过几句、花过多少。

字段作用例子
identity主键和 event.identity 同一把钥匙。anon 的事件不建这一行uid:15247
uid写不读B 站 uid，打码时为 0。identity 已经含它，没人单独读15247
uid_hash写不读打码时平台给的稳定哈希。同上（空）
uname最近一次见到的昵称，新名字非空才覆盖。常客段和蒸馏名单用它称呼人yiang
guard_level写不读舰队等级 none / captain / admiral / governor。只有带真实等级的事件才覆盖，进房事件不会把它抹成 none。今天没有读者none（本机 11 个 captain）
first_seen写不读第一次见到2026-08-10T21:39:36+00:00
last_seen写不读最近一次见到2026-09-22T03:48:14+00:00
streams_seen来过几场。只在 last_stream_id 和当前场不同时 +1，所以一场里刷一百条也只算一次。常客门槛是 ≥ 27
last_stream_id索引最近出现在哪一场。「本场在场的常客」就是 WHERE last_stream_id = 当前场161
msg_count说过几句。只有带正文的事件 +1，礼物和进房不算8
gift_value_cny累计花了多少钱。蒸馏挑「前 20 名观众」先按它排1360.0
寿命：永久，从不删。本机 612 行：46 个有 uid、566 个打码哈希；87 人来过两场以上，绝大多数是测试卡和 Mock 的合成观众。

fact 蒸馏出的结论

唯一经过模型的表。(scope, subject) 是一组，写的时候整组先删后插，所以一场永远只有一条摘要、一个观众永远只有一条事实。

字段作用例子
id主键自增，同组内按它排序取最后一条40
scope索引哪方面：stream 本场进展、viewer 某个观众、streamer 主播本人（有读者、没有写入方，永远 0 行）stream
subject索引谁的。scope=stream 时是 stream.id，scope=viewer 时是 viewer.identity，scope=streamer 时为空串161 / uid:15247
text结论正文。本场摘要 ≤ 200 字，观众事实 ≤ 40 字yiáng，老粉，高消费，关注游戏机制与细节
tags写不读计划里的标签检索列。蒸馏已不再向模型索要，模型自愿给的才落库，全仓没有读者8 月旧行：关注直播分工,偏好互动细节,高粘性粉丝
created_at写不读写入时刻。facts() 不选这一列2026-09-22T04:22:59+00:00
寿命：同组覆盖。本机 47 行：stream 40、viewer 7、streamer 0。旧场的 39 条摘要再也没人读。

表之间怎么连

  • event.stream_id → stream.id：一场有很多事件。读事件时永远先按当前场过滤。
  • viewer.last_stream_id → stream.id：这个人最近出现在哪一场。等于当前场就是「在场」。
  • event.identity = viewer.identity：同一把钥匙，但不是外键，anon 的事件没有对应观众行。
  • fact.subject → viewer.identity 或 stream.id，看 scope。全是字符串，没有约束。

全库没有外键、没有迁移脚本：建表全是 CREATE TABLE IF NOT EXISTS，加列要自己想办法。时间全是 UTC ISO 字符串，「直播日」按北京时间 04:00 翻（通宵场算同一天）。

谁来查什么

库上一共只有九种读法。左边是业务上在问什么，右边是谁在什么时候问。

所有读之前都先把攒批写（write_batch_ms，出厂 0 即关）刷进库，所以读到的永远是最新的。

几条设计上的规矩

谁是谁：identity 三选一有 uid 用 uid:15247；被平台打码只剩哈希用 hash:41cf8adf；两者都没有就是 anon。真房间里绝大多数是哈希（本机 566 比 46）。
anon 不建观众行房间状态这类没人的事件只记事件行。代价：打码到连哈希都没有的送礼人，礼物算不到任何人头上（本机 4 条礼物行全是 anon）。
一场只算一次来访streams_seen 靠 last_stream_id 变化才加，不靠事件数。所以它是「来过几场」不是「来过几次」。
等级只升不降guard_level 只被带真实等级的事件覆盖。好处是进房事件不会把舰长抹成普通人；代价是过期的舰长要等下一条带等级的事件才会更正。
主播自己的字要认得出主播在自己房间打的弹幕，uname 写成「主播本人·名字」，蒸馏读事件列表时就不会把它当成观众在提要求。
时间两套行里存 UTC 字符串，机器无关；算「直播日」和「本周」时转北京时间再往前挪 4 小时，通宵场归前一天。
写法两档出厂每个事件一个事务，当场落盘。write_batch_ms > 0 改成攒批：满 200 行或到时间一次写，任何读之前先刷，崩了最多丢一个窗口的事件行。
结论整组覆盖fact 没有「更新一条」，只有「把这组全删了重写」。好处是表有界、不会积累矛盾的旧结论；代价是蒸馏一次写坏，旧的也没了。

看表时顺手发现的

不算 bug，但重构时要知道。

  1. 六个字段写了没人读stream.ended_at、viewer.uid / uid_hash / guard_level / first_seen / last_seen、fact.tags / created_at。读进 ViewerRow 的字段里，真被用上的只有 identity、uname、streams_seen、msg_count、gift_value_cny。
  2. 一个公开方法没人调store.viewer(identity)。UPSERT 注释里说「VIP 晋升会读等级」，实际晋升读的是事件自带的等级，不查库。
  3. 旧场摘要是死数据scope=stream 的五个读者全按当前场查，上一场的摘要留在库里再没人读。本机 40 条里 39 条是这种。
  4. 库不按房间分路径写死 rooms/dev-talk/memory.db，配置里的 memory.db_path 没有读者。合成观众永久混在 viewer 里，612 个里真人很少。
  5. 开播行可能收不了尾begin_stream() 在主 try 之前，连接失败、词表缺失这类启动期退出，留下 ended_at 为空的行，而「本周第几场」照数。
  6. 主播说的话、她说的话都不在这里只有观众事件。主播转写和她的回复只在进程内存里，所以「主播」那一段永远 0 行。
